# CLAUDE.md (web_version)

`desktop_version`(PyTorch)에서 학습한 모델을 브라우저에서 그대로 돌리는 순수 자바스크립트
인식기. 학습은 하지 않고 인식만 한다. GitHub Pages 에 정적 파일로 올라간다.
공통 규약(한글 이름, 작성일시 주석)은 루트 `../CLAUDE.md` 를 따른다.

## 가장 중요한 규칙: 외부 의존성 없음

**외부 라이브러리·빌드 도구·패키지 매니저를 쓰지 않는다.** `package.json` 도 만들지 않는다.
GitHub Pages 에 그대로 올라가는 정적 파일이어야 하고, 의존성이 생기면 그 전제가 무너진다.
새 기능이 필요하면 직접 짠다(예: PIL Lanczos 다운스케일을 손으로 이식한 `전처리.js`).

## 명령

아래는 모두 이 폴더(`web_version/`) 안에서 실행한다.

```
node 점검.mjs                                    # JS 이식 검증 (유일한 검증 경로)
../venv/Scripts/python.exe 도구/내보내기.py       # mnist_cnn.pt -> 가중치.bin + 기준값.json
../venv/Scripts/python.exe -m http.server 8765   # 로컬에서 띄우기 (열람: localhost:8765)
```

`내보내기.py` 는 torch 가 필요해 데스크톱 환경(`../venv`, 저장소 루트)에서 돈다.
**`file://` 로 index.html 을 직접 열면 안 된다** — ES 모듈(`import`)이 CORS 에 막혀
아무것도 뜨지 않는다. 반드시 위의 `http.server` 같은 로컬 서버로 띄운다.

## 기준선 (`node 점검.mjs` 출력)

- **1단계 추론 엔진**: 10/10 정답, 최대 확률차 `5.96e-8` (허용 `1e-5`, `design.md` 의
  절대 오차 목표와 맞춘 값)
- **2단계 전처리**: 최대 화소차 `0` (허용 `0`) — 화소가 하나도 안 어긋난다.
  설계 시 허용오차 1 정도의 여유를 잡아 두었지만 실측에서는 필요 없었다.
- 비교 대상인 데스크톱 쪽 기준선: MNIST 99.10%(9910/10000), 그린 획 10/10
  (`../desktop_version/CLAUDE.md` 참고)
- **float16 양자화 비용**: `+0.000%p` (float32 99.10% → float16 99.10%, `내보내기.py` 가 측정)
- `가중치.bin` 크기: 정확히 `2,399,764` 바이트. 이 값이 달라지면 모델 구조가 바뀐 것이다.

## 전처리 계약

`전처리.js` 의 `그림_전처리` 는 `../desktop_version/app.py` 의 같은 이름 함수와 쌍이다.
**한쪽만 고치면 안 된다.** 고쳤으면 `../venv/Scripts/python.exe 도구/내보내기.py` 로
기준값을 다시 만들고 `node 점검.mjs` 를 돌려 확인한다.

## 28x28 축소에 canvas `drawImage` 를 쓰지 않는다

`전처리.js` 는 280x280 → 28x28 축소를 PIL 의 Lanczos 리샘플링을 고정소수점 계산까지
그대로 손으로 옮겨서 한다. **`ctx.drawImage(캔버스, 0, 0, 28, 28)` 이나
`imageSmoothingQuality` 같은 브라우저 canvas 의 내장 축소 기능을 쓰지 않는다.**

이유는 둘이다.

1. 브라우저 canvas 의 보간 방식은 브라우저마다(때로는 버전마다) 달라서, 파이썬(PIL)
   쪽과 화소 단위로 맞출 방법이 없다.
2. 더 중요한 것은 **검증이 아예 불가능해진다는 점**이다. `점검.mjs` 는 Node 에서 도는데
   Node 에는 canvas 가 없다. `drawImage` 를 쓰면 `전처리.js` 를 Node 에서 그대로 실행할
   수 없으므로, 배포되는 코드와 검증하는 코드가 갈라진다 — 위 입출력 경계 규칙이 막으려는
   것과 같은 종류의 문제다.

그래서 200여 줄짜리 리샘플러가 들어 있는 것은 실수나 과잉 구현이 아니라 의도다.
"`drawImage` 한 줄이면 될 것 같다"는 생각이 들어도 바꾸지 말 것 — 바꾸면 파이썬-JS
동등성을 보장하는 검증 스위트 전체의 전제가 조용히 무너진다.

## 입출력 경계: `모델.js`·`전처리.js` 는 I/O 를 하지 않는다

**`모델.js` 와 `전처리.js` 는 `fetch`·`document`·`node:` 모듈을 쓰지 않는다.**
입출력은 `앱.js`(브라우저에서 `fetch` 로 가중치를 읽고 canvas 를 다룬다)와
`점검.mjs`(Node 에서 `node:fs` 로 파일을 읽는다)가 맡는다.

이 경계 덕분에 **배포되는 코드(`모델.js`, `전처리.js`)를 고치지 않고 그대로 Node 에서
검증할 수 있다.** 이 규칙을 깨면(예: `모델.js` 안에서 직접 `fetch` 를 부르면) 검증이
불가능해진다 — `점검.mjs` 가 실제로 돌리는 코드와 브라우저가 돌리는 코드가 달라지기 때문이다.

## 검증의 경계: 무엇을 보장하고 무엇을 보장하지 않는가

PIL 의 `ImageDraw` 는 안티앨리어싱을 하지 않지만 브라우저 canvas 는 한다. 그래서 **같은
마우스 궤적이 양쪽에서 같은 280x280 비트맵이 되는 일은 없다** — 이것은 애초에 불가능하고
목표도 아니다.

`점검.mjs` 가 실제로 보장하는 것은: **같은 280x280 입력이 주어지면, 같은 28x28 과 같은
확률이 나온다.** 즉 전처리·추론 로직의 이식이 맞았는지를 보장하지, 손으로 그린 그림이
데스크톱과 웹에서 똑같이 보인다는 것을 보장하지 않는다.

### 골든 세트에서 숫자 0 이 하는 일

`기준값.json` 의 골든 벡터 중 **숫자 0 은 특별히 중요하다.** 이 벡터의 무게중심 이동량이
`13.5 - x합/총합 == 0.5` 를 정확히 만족하는 **반올림 동점(tie) 케이스**다. 이것이
붙여넣기(paste) 오프셋과 `파이썬_반올림`(은행가 반올림) 양쪽을 동시에 고정하는 유일한
벡터다 — 나머지 아홉 숫자는 이 두 가지가 틀려도 통과할 수 있다. 무게중심 재정렬이
±1 정도의 붙여넣기 오차를 흡수해 버리기 때문이다.

**골든 세트를 다시 만들 일이 있으면 동점 케이스를 반드시 하나 남겨 둘 것.** 그러지 않으면
이 민감도가 조용히 사라지고, `점검.mjs` 가 통과해도 반올림 방식이 틀린 이식을 잡아내지
못하게 된다.

## 기준값은 float16 양자화 모델에서 뽑는다

`기준값.json` 의 `기대_확률` 은 **float16 으로 양자화한 모델**(웹이 실제로 쓰는 것과 같은
가중치)의 출력이다. float32 원본 모델 값을 쓰면 JS 와 비교할 때 "이식 오류"와
"float16 양자화 오차"가 섞여서, 이식이 맞았는지 양자화 탓인지 구분할 수 없게 된다.

## 모델 구조를 바꾸면

`../desktop_version/model.py` 의 `숫자인식CNN` 을 바꾸면 **재학습**(`train.py`)과
**`도구/내보내기.py` 재실행**이 둘 다 필요하고, `모델.js` 의 순전파도 같이 고쳐야 한다.
`내보내기.py` 는 `state_dict` 의 텐서 이름·순서·모양이 예상과 다르면 그 자리에서 멈춘다 —
단 이 검사는 **내보내기를 실행했을 때만** 작동하고 이름·모양만 보므로, 구조 변경을 하고도
재내보내기를 잊으면 걸린다.

이것만으로는 안 잡히는 구멍이 있었다: 구조는 그대로 두고 에폭만 늘리는 **평범한 재학습**은
이름·모양이 그대로라 위 검사를 통과해 버린다. 그 상태로 재내보내기를 잊으면
`기준값.json`·`가중치.bin` 은 예전 것끼리 계속 서로 맞으므로 `node 점검.mjs` 가 영원히
통과하고, 데스크톱과 웹이 서로 다른 가중치를 조용히 서비스하게 된다. 그래서 `점검.mjs` 의
0단계가 `../desktop_version/mnist_cnn.pt` 원본 바이트의 SHA-256 을 `가중치_구조.json` 의
`원본_sha256` 과 대조한다 — 재학습으로 파일 내용이 바뀌었는데 재내보내기를 안 했으면
지문이 달라져 검증이 실패한다. (데스크톱 쪽 파일이 아예 없는 CI 환경 등에서는 대조를
건너뛰고 통과시킨다 — 이 경우 이 단계는 아무것도 확인하지 못한 것이다.)

## 배포

main 브랜치에 push 되면 `../.github/workflows/웹_배포.yml` 이 `node 점검.mjs` 로 검증한
뒤 `web_version/` 을 GitHub Pages 에 올린다. **저장소 Settings → Pages 의 Source 가
"GitHub Actions" 로 설정되어 있어야** 실제로 배포된다(코드로는 바꿀 수 없다).

이 워크플로의 job id(`verify`, `deploy`)와 step id(`deploy_step`)는 영문이다.
GitHub Actions 는 id 에 한글을 허용하지 않아(파싱 자체가 실패) 어쩔 수 없이 예외를
둔 것이고, 사람이 읽는 `name:` 과 주석은 전부 한글이다. `environment.name` 에 쓰인
`github-pages` 도 같은 이유의 예외다 — GitHub Pages 배포가 인식하는 고정 환경
이름이라 글자 그대로 써야 한다. `index.html` 파일명과 같은 종류의 예외로 취급할 것.

## 생성물은 커밋한다

`가중치.bin`·`가중치_구조.json`·`기준값.json` 은 `도구/내보내기.py` 로 다시 만들 수
있지만, **커밋한다** — 클론한 즉시 사이트가 동작해야 하고, CI 검증(`웹_배포.yml` 의
`node 점검.mjs`)도 이 파일들을 그대로 읽기 때문이다.
